# 1.1 plan

What turned up on `1.0.1`, from reading the `date` surface and then asking
why a counting loop is as fast as CPython.

Each entry says what was run, what happened, where the code is, and which
clause it contradicts — so the decision can be about whether to fix it, not
about whether it is real.

Companion to [`RC7-PLAN.md`](RC7-PLAN.md) and [`RC8-PLAN.md`](RC8-PLAN.md),
both closed. Item 11 of RC7 (`parallel { }`) is still open and still 1.1;
this plan does not reopen it.

## 1. `date.parse` never parses

**Class:** wrong status · `src/exec_call.rs:688`

```rust
"date.parse" => Value::Timestamptz(s(0)),
```

The input is wrapped as a `Timestamptz` and returned. `builtins.md §3` types
it `timestamptz?`, and the `?` is the whole contract: a string that is not a
timestamp comes back null. It never does.

What makes this worse than the `boolean(x)` defect rc.7 fixed is that the
type system pushes the author into a guard, and then the guard is dead code.
`timestamptz?` is not assignable to a `NOT NULL` column (`E0606`), so the
program has to be written this way:

```jwc
let t = date.parse(@raw) or throw BadRequest("sana yaroqsiz");
```

Measured, against a real Postgres:

```
?t=2026-03-01T10:00:00Z  →  200
?t=kecha                 →  500
     [fault] invalid input syntax for type timestamp with time zone: "kecha"
```

The `or throw` never fires. The author did everything the compiler asked and
still got a 500 where they wrote a 400.

**Proposal.** Parse it. `chrono` is already a dependency and `date(x)` eleven
lines below already validates, with a comment giving the reason: *"a `date`
this rejects is one Postgres would have rejected later, with a fault instead
of a sentence."*

## 2. `date.format` ignores the format string

**Class:** soundness · `src/exec_call.rs:689`

```rust
"date.format" => Value::Text(s(0)),
```

It returns the first argument as text. The second is never read.

```
date.format(date.now(), "%Y-%m-%d %H:%M")
  →  2026-09-29T12:27:02.972380Z
```

`builtins.md §3` says `fmt` is *"a literal, checked at compile time"*. It is
neither checked nor used: `date.format(t, "butunlay-buzuq-%Q%Z%%")` compiles
clean and returns the same RFC 3339 string.

This is the only entry on the list that is a **silent wrong answer** — no
error, no 500, just a different string than the one asked for. A report
formatted for a human reads as an ISO timestamp and nobody finds out from
the program.

**Proposal.** Implement it, or remove it. A builtin that quietly ignores an
argument is worse than one that does not exist, because the call site looks
correct in review.

## 3. A typed path parameter is not validated for five types

**Class:** wrong status · `src/serve.rs:613`

The match that parses `{name: T}` has arms for `bigint`, `int`/`smallint`,
`numeric`, `boolean` and `uuid`, then:

```rust
_ => Some(Value::Text(raw.clone())),
```

So `date`, `timestamptz`, `time`, `inet` and `bytea` are accepted as raw
text. `routing.md §3.1` says `T` is *"a scalar type (types §2.1)"* — all five
qualify — and §3.2 promises the refusal:

```
400 {"error":"bad_path_parameter","parameter":"org_id","expected":"bigint"}
```

with the reason written beside it: *"This is the fix for #20: malformed
input reached Postgres and became a 500."* Measured, on a table with
`held_on date`:

```
/n/kecha             →  400  bad_path_parameter          ← bigint, correct
/lessons/kecha       →  500  [fault] invalid input syntax for type date
/lessons/2026-02-30  →  500  [fault] date/time field value out of range
```

The second one is the interesting failure: `2026-02-30` is shaped like a
date. Nothing short of a real calendar parse rejects it, and Postgres is
doing that parse on the far side of the query.

**Proposal.** An arm per type. `date` and `timestamptz` are a `chrono` parse;
`inet` and `bytea` have crates already in the tree. The catch-all then means
`text`/`varchar` only, which is what it was for.

## 4. `interval` is write-only, and loses everything under a second

**Class:** gap

`date.days/hours/minutes/seconds(n)` build one, `+` and `-` combine them,
`string.of` prints one. Nothing reads a number back out — `interval` carries
no fields (`E0312`) and there is no builtin, in 1.0.1 or before.

It is also truncated. `timestamptz` is microseconds on the wire; the
difference of two of them is not:

| real elapsed | `string.of(a - b)` |
|---|---|
| 0.176 s | `PT0S` |
| 1.248 s | `PT1S` |

Together these mean a program cannot time itself. The only route to a number
today is to parse the ISO 8601 string the language prints:

```jwc
let secs = int(string.replace(string.strip_prefix(string.of(elapsed), "PT"), "S", ""));
```

which is what the benchmark below had to do, and which is wrong for any
interval a day or longer (`P1DT2S`).

Inside a request `response.duration_ms()` and `duration_us()` exist and are
accurate; outside one there is nothing.

**Proposal.** Two parts, and the first is the cheap one: keep the fractional
seconds through the subtraction, since both operands carry them. Then either
`interval` grows accessors, or `date.millis(i)`/`date.micros(i)` gain
inverses. The second is a surface decision and belongs with the rest of 1.1.

## 5. The generated code boxes a local whose type the checker already knows

**Class:** performance · **measured 8.7× · fixed**

`jwc build --release`, one billion iterations of `count = count + 1`:

| | 1e9 | vs shipped |
|---|---|---|
| **as shipped** | **58.1 s** | 1× |
| without the `% 1024` yield and the turn ceiling | 41.3 s | 1.4× |
| **`i64` locals**, ceiling and yield kept | **6.6 s** | **8.7×** |
| `i64` and neither | 0.003 s | LLVM deleted the loop |

Same machine, for scale: C at `gcc -O2` with `volatile` is **0.42 s**, and
CPython 3.11 is **~66 s**. As shipped, the AOT backend is **1.06× CPython**
on integer arithmetic. With `i64` locals it is 16× off C.

`--emit-rust` shows why. One turn of the inner loop:

```rust
if !jwc_truthy(&V::Bool(jwc_lt(&v_j.clone(), &V::Int(1000000)))) { break; }
__turns += 1;
if __turns > 10000000 { return Err(...); }
if __turns % 1024 == 0 { ::tokio::task::yield_now().await; }
v_count = jwc_add(v_count.clone(), V::Int(1));
v_j     = jwc_add(v_j.clone(), V::Int(1));
```

Four `V` clones, three dynamic calls, a modulo and two bounds checks, for
what is one `add` instruction. Three separate things are paying:

- **`V` for a local the checker typed.** `let count = 0` is an `int` at check
  time and never escapes into a dynamic context. The type information exists
  and the backend does not use it. This is the 8.7×.
- **`V::Bool(jwc_lt(…))` then `jwc_truthy(…)`.** `jwc_lt` returns `bool`
  (`:1022`). It is wrapped and immediately unwrapped, in the condition of
  every loop in every program.
- **`jwc_add` asks "timestamp + interval?" first.** `jwc_ts_shift(&a, &b, 1)`
  is the first line of the function (`:846`), so every `i + 1` pays a
  timestamp check before reaching the integer arm.

The second and third are small and local. The first is the one worth
planning: a `let` whose inferred type is a scalar and whose address is never
taken can be a native `i64` / `f64` / `bool`, with `V` only at the boundary
where it meets something dynamic.

**Also worth deciding:** the `% 1024` yield exists so `request_timeout` can
fire on a compute-bound loop (config.md §6a.1, and the measurement there is
real). In a `main()` console program there is no request and no timeout, and
it is worth 1.4× on its own.

**Caveat on the last row.** 0.003 s is not a result — once the loop is plain
integer arithmetic with no side effects, LLVM proves the answer and deletes
it. The same is true of hand-written Rust: the program this benchmark was
compared against reports `162` and exits in 2 ms, because its loop is gone
too and `as_nanos()` was labelled `ms`. Row three is the honest number.

**Fixed.** A `let` whose initialiser and every later write are integer
arithmetic over literals and other such locals is an `i64`; a condition
over two of them is a Rust comparison; `jwc_add` asks about integers before
timestamps. Which locals qualify is decided once per body — the largest set
that only reads itself — so `total = total + k` qualifies when `k` does.
Re-measured on one machine, back to back:

| | 1e9 |
|---|---|
| `1.0.1` | 57.3 s |
| this branch | **7.0 s** (8.2×) |

The yield and the turn ceiling are kept. The arithmetic is checked, which
also fixed a parity defect nobody had written down: the native integer arms
were plain `x + y`, so in a release binary `i64::MAX + 1` wrapped where
`jwc serve` answered 500. `tests/native_parity` is diffed across both
backends in CI, and one past `i64::MAX` is checked to be refused by both.

## 6. Every project recompiles the dependency tree

**Class:** ergonomics

The billion-iteration program is 20 lines of JWC. `jwc build --emit-rust`
produced **6,195 lines**, of which **41** are the program, and its first
release build took **78 s**. The prelude looked like the cost, and the
proposal was to move it into a `jwc-runtime` crate cargo could cache.

**Measured, that was the wrong suspect.** The same program, its crate
already built once:

| | |
|---|---|
| first debug build, empty target directory | 27.2 s |
| debug rebuild — prelude and program recompiled, dependencies cached | **2.1 s** |
| release rebuild, dependencies cached | 43.9 s |

The prelude and the program together compile in two seconds. The 27 s is
tokio, hyper, serde and the tree under them, and it was paid by every
project because each had a target directory of its own under
`.jwc-build/`. A `jwc-runtime` crate would have saved the two seconds and
none of the rest. The release figure is fat LTO with one codegen unit over
the whole tree — a per-binary cost no crate split removes, and the price of
the profile being tuned for speed (PERF_PLAN A5).

**Fixed.** Every project now builds into one shared target directory,
`~/.jwc/cache/target`, so the dependency tree compiles once per toolchain
and feature set. Two fresh projects, one after the other:

| | first debug build |
|---|---|
| the first, cache empty | 22.2 s |
| the second, a different project | **5.5 s** |

`JWC_BUILD_CACHE` names another directory or `off`; `CARGO_TARGET_DIR`
wins over both. A lock beside the cache holds from the start of the cargo
run until the binary has been copied out, so two projects with the same
name cannot take each other's binary.

## 7. The binary carries Apache-2.0 code and nothing declares it

**Class:** legal · **Found:** vendoring Swagger UI

`vendor/swagger-ui/` puts swagger-ui-dist 5.33.1 inside every `jwc` binary.
Its `LICENSE` (Apache-2.0) and the two `*.LICENSE.txt` dependency notices
webpack emitted are checked in beside the assets, which satisfies "include a
copy" — but nothing in a *distributed binary* points at them, and §4 of the
licence is about what accompanies the distribution, not what sits in the
source tree.

The gap is wider than the new files. The project has **no `LICENSE` of its
own**: `Cargo.toml` carries

```toml
# Workspace-private until a license decision lands (see deny.toml [licenses]
# …) so cargo-deny correctly classifies this crate as private and skips the
# unlicensed check.
```

and `cargo deny` runs in CI over Rust crates, so it never sees a vendored
JavaScript bundle either way. Releases have been publishing binaries since
0.9.x on that footing.

Two separate things, and only the first is new here:

| | |
|---|---|
| **Third-party notice** | a `NOTICE` the release carries, listing what is compiled in and under what licence. Today that is Swagger UI; `cargo deny list` already knows the Rust side |
| **The project's own licence** | the decision `Cargo.toml` is waiting on. Not caused by this change, but a binary with no licence at all is the larger of the two |

**Proposal.** Write `NOTICE` from the vendored tree plus `cargo deny list`,
attach it to the release the way the `.sha256` files are attached, and have a
test assert that every directory under `vendor/` appears in it — the same
shape as the guards that keep the docs honest, so the next vendored thing
cannot be forgotten. The project's own licence is a decision rather than a
task and stays where it is, named here so it is not discovered at the next
release.

## 8. `numeric` arithmetic is wrong on both backends

**Class:** soundness · **fixed**

types.md §2.2: a fractional literal "is never a binary float". §12.2: `/`
with a `numeric` operand is exact division. Neither backend did either.

```jwc
console.writeln(string.of(1.5 + 2.25));
console.writeln(string.of(12345678901234.56 + 0.01));
console.writeln(string.of(2.5 * 2));
```

| | `jwc run` 1.0.1 | `jwc build` 1.0.1 |
|---|---|---|
| `1.5 + 2.25` | `3.75` | **`1.52.25`** |
| `12345678901234.56 + 0.01` | **`12345678901234.570312`** | — |
| `2.5 * 2` | `5` | **panic** |
| `1 / 3.0` | `0.333333` | — |

The interpreter's `numeric_op` (`exec.rs`) converted both sides to `f64`
and printed six places. The native backend holds a `numeric` as `V::Str` —
its wire form — so `jwc_add` took the string arm and concatenated, and
`jwc_mul` had no arm at all.

Then a column, which is where money actually comes from. A `bigint` and a
`numeric` are read back from Postgres in their wire form, a string, and
nothing in the value says it is a number. `price numeric(12,2) = 19.99`,
`qty int = 3`, under `jwc serve` 1.0.1:

| | answered |
|---|---|
| `it.price + it.price` | `"19.9919.99"` |
| `string.of(it.id + it.id)` | `"11"` |
| `it.price * it.qty` | 500 |
| `-it.price` | 500 |

**Fixed.** `src/numeric_core.rs.in` is decimal arithmetic that both
backends include, exact for `+ - *` and 28 significant digits for a `/`
that does not terminate. The checker marks every `+ - * / %` and unary `-`
with the arithmetic it is (`ast::ArithMark`) and both backends read the
operands as that, so a string from a column is a number where the declared
type says it is. The mark lives on the AST node, not in a side table,
because the interpreter runs a clone of the tree. `jwc serve` runs a second
checker pass at load for the marks alone, so the result of a function call
is typed — see entry 10 for why the first pass does not.
`tests/native_parity` is diffed across the two backends in CI.

## 9. A `bigint` is a JSON number in a native binary

**Class:** soundness · open

```jwc
routes "/p/{id: bigint}" {
    route GET "/h" {
        return json({ v: @id, w: @id + 1, b: bigint("7") });
    }
}
```

| | `GET /p/1/h` |
|---|---|
| `jwc serve` | `{"v":"1","w":"2","b":"7"}` |
| `jwc build` | `{"v":1,"w":2,"b":7}` |

types.md §2.3: "`bigint` and `numeric` serialise as JSON **strings**, on
the raw path and the record path alike, in every direction." The
interpreter has `Value::Bigint`, which serialises as a string. `V` has only
`V::Int`, which serialises as a number, so the native binary cannot tell a
`bigint` from an `int` when it writes JSON — and above 2^53 a JavaScript
client rounds the id.

`docs/docs/cli/index.md` says the release check compares the two backends'
responses byte for byte. This is a response where they differ, for every
`bigint` that is not read straight out of a raw query.

**Proposal.** A `V::Big(i64)`, as the interpreter has: built by
`bigint(x)`, a `bigint` path parameter, a `bigint` body field and
`jwc_int_op` when either side is one, and written as a string. The other
direction — knowing at codegen which fields of a literal are `bigint` —
fails for anything that reaches `json()` through a function.

## 10. `jwc check` runs the checker once

**Class:** soundness · open

```jwc
service Shop {
    function one(id: bigint) {
        return select I from App.shop.Items
            where I.id == @id
            as { I.id, I.price, I.qty }
            first or throw NotFound("no item");
    }
}

routes "/items/{id: bigint}" {
    route GET "" {
        let it = Shop.one(@id);
        let y: boolean = it.price;      // accepted
        return json(@it);
    }
}
```

`jwc check` says `ok`. With the same `select` written inline, it is
`E0352: numeric is not assignable to boolean`. One pass cannot know what a
function it has not reached returns — and an unannotated function has no
declared return, so `known_returns` (`check.rs`) is empty on the only pass
there is, and **every** call to one is `Unknown` at its call site, declared
before it or not. Nothing about its result is checked.

`jwc openapi` already ran two passes. On this branch `jwc build` and
`jwc serve` run the second too, for entry 8's marks, without reporting what
it finds.

**Proposal.** Two passes in `jwc check` and wherever diagnostics are
reported. The decision is the release: a program that passes today can
fail tomorrow, correctly — every new error is a real type error that was
being let through.

## 11. `jwc build` refuses all three real applications

**Class:** gap · open

| | `jwc build` 1.0.1 and this branch |
|---|---|
| e-school | `view` not covered — eleven of them |
| MyWallet | `cannot resolve the bare name Categories outside a query` — an `insert … as { Categories.id, … }` |
| jwc-shortener | `cannot resolve the bare name Links outside a query` — an `insert Links into … { } catch Conflict (err) { continue; };` |

Each is refused by name, which is the designed behaviour, and each
application runs under `jwc serve`. But it means the parity claim in
`docs/docs/cli/index.md` is not being exercised on any of them, and that
entries 8 and 9 were found by a 50-line probe rather than by the release
check. The three were also still on rc.6 syntax (`) -> T`), which 1.0
refuses (`E0906`) — moved for this measurement only, in a copy.

**Proposal.** Lower the `insert … as { }` projection and the `insert`
statement with a postfix `catch` first — both are one construct each and
cover two of the three applications. Views are a project of their own.

## What is left

Entries 1 to 8 are done on this branch. What remains needs a decision
before it needs work:

1. **10** — two checker passes in `jwc check`. Small to write; the question
   is whether 1.1 may reject a program 1.0.1 accepted, when what it rejects
